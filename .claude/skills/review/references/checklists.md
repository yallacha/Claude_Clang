# 산출물별 리뷰 체크리스트 (A-SPICE 기반 기본 틀)

프로젝트에 맞게 항목을 추가·수정하고 변경 이력을 남긴다.

## 1. 소프트웨어 요구사항 명세 (SWE.1)
- [ ] 기능 / 비기능 요구사항이 구분되어 있는가
- [ ] 기능 안전 요구사항이 별도 문서에서 관리되고 참조만 되어 있는가
- [ ] 비기능 요구사항이 품질 / 제한 / 제약사항으로 구분되어 있는가
- [ ] 품질 요구사항이 ISO/IEC 25010 특성으로 분류되고 측정 가능한 기준이 있는가
- [ ] 각 요구사항이 단일하고 모호하지 않으며 검증 가능한가
- [ ] 요구사항 간 충돌·중복이 없는가
- [ ] 필수 속성(ID, 근거, 우선순위, 검증 방법, 상태)이 있는가
- [ ] 시스템 요구사항과 양방향 추적이 되며 고아 항목이 없는가
- [ ] 요구사항이 아키텍처/테스트와 양방향 추적 가능한 상태인가

## 2. 소프트웨어 아키텍처 설계 (SWE.2)
- [ ] 모든 컴포넌트가 정의되고 책임이 단일한가
- [ ] 모든 컴포넌트에 인터페이스(시그니처, 범위, 오류, 조건)가 정의되어 있는가
- [ ] 컴포넌트 간 통신이 인터페이스로만 이루어지는가 (직접 접근/전역 공유 없음)
- [ ] 높은 응집도·낮은 결합도이며 순환 의존이 없는가
- [ ] 모듈화·캡슐화·SOLID 원칙을 준수하는가
- [ ] 동적 거동과 자원 소비 목표가 기술되어 있는가
- [ ] 모든 SW 요구사항이 컴포넌트에 할당되어 있는가 (양방향 추적)
- [ ] 설계 결정의 근거가 기록되어 있는가

## 3. 소프트웨어 상세 설계 (SWE.3)
- [ ] 모듈과 함수가 정의되고 컴포넌트와 추적되는가
- [ ] 기준 이상 모듈에 인터페이스가 정의되어 있는가
- [ ] 인터페이스 정의 모듈 간 통신이 인터페이스로만 이루어지는가
- [ ] 함수·모듈이 단일 책임 원칙을 만족하는가
- [ ] 클린코드 원칙(명명, 작은 함수, 중복 없음, 매직 넘버 없음)을 만족하는가
- [ ] 함수별 입력·출력·리턴값·오류 처리가 기술되어 있는가
- [ ] 아키텍처 및 요구사항과 일관되고 양방향 추적되는가

## 4. 소스 코드 (구현)
- [ ] 프로덕션 코드의 모든 함수가 리턴값을 가지는가 (`void` 없음; gtest `TEST()` 본문은 예외)
- [ ] 프로덕션 코드의 리턴문이 함수 마지막에 단 한 번만 존재하는가
- [ ] 리턴값이 없는 경우 정상 실행 여부를 알 수 있는 상태 값을 리턴하는가
- [ ] 호출자가 리턴값을 확인·처리하는가
- [ ] 상세 설계와 일치하며 설계에 없는 동작이 없는가
- [ ] 내부 함수/데이터가 은닉(`static`)되어 있고 인터페이스를 통해서만 접근되는가
- [ ] 컴파일러 경고 0
- [ ] CppCheck 위반 0건이며 억제 주석/억제 파일이 없는가 (결과를 직접 실행해 확인)
- [ ] Lizard: 모든 함수가 순환복잡도 10 이하, 함수 라인수 80 이하인가 (직접 실행해 확인)
- [ ] 소스·함수 주석이 Doxygen 형식이며 AI 작성 정보(모델, 일시, 요청자)가 있는가
- [ ] 리뷰 상태(Human Review) 태그가 있고, 사용자 리뷰 전 코드는 `Not Reviewed`인가 (임의로 `Reviewed` 표기 금지)
- [ ] TDD 테스트가 `tests/tdd/`에 분리되어 있고 별도 결과·별도 커버리지로 산출되었는가 (단위 테스트 커버리지에 합산 금지)
- [ ] 각 기능에 대해 테스트가 먼저 실패했음(RED)을 확인한 증거가 있는가
- [ ] 상세 설계와의 추적성이 유지되는가

## 5. 단위 테스트 (SWE.4)
- [ ] 테스트가 상세 설계/요구사항과 양방향 추적되는가
- [ ] 모든 테스트 함수에 Doxygen 주석(목적, 입력값, 절차, 예상 출력값)이 있는가
- [ ] 경계값 분석·동치 클래스·PICT 조합이 적용되었는가
- [ ] **MC/DC 커버리지 100%**를 LLVM 리포트로 직접 확인했는가 (제외 항목 없음, 테스트 코드·gtest 제외 설정 확인)
- [ ] **테스트 성공률 100%**인가 (실패·스킵·비활성 테스트 없음, 실행 결과를 직접 확인)
- [ ] 커버리지가 `tests/unit/`만으로 측정되었고 TDD 테스트(`tests/tdd/`)가 합산되지 않았는가
- [ ] 테스트 함수 주석에 AI 작성 정보와 리뷰 상태(Human in the Loop) 태그가 있는가
- [ ] 의미 없는(단언 없는/커버리지용) 테스트가 없는가
- [ ] Stub/Mock이 필요한 곳에만, 과하지 않게 사용되었는가
- [ ] 예상 결과가 설계/요구사항에서 도출되었는가 (구현 코드를 베끼지 않음)
- [ ] 테스트가 반복 실행 시 동일한 결과를 내는가

## 6. 통합 테스트 (SWE.5)
- [ ] 인터페이스 중심의 컴포넌트 연동 테스트로 구성되어 있는가
- [ ] 모든 인터페이스와 대상 요구사항에 테스트가 있고 양방향 추적되는가
- [ ] 정상/오류/경계/순서·타이밍 조건이 검증되는가
- [ ] 모든 테스트 함수에 Doxygen 주석(목적, 입력값, 절차, 예상 출력값)이 있는가
- [ ] 경계값 분석·동치 클래스·PICT 조합이 적용되었는가
- [ ] **함수 커버리지 100%**를 LLVM 리포트(Functions/Missed Functions)로 직접 확인했는가
- [ ] **테스트 성공률 100%**인가 (실패·스킵·비활성 테스트 없음, 실행 결과를 직접 확인)
- [ ] 커버리지가 `tests/integration/`만으로 측정되었는가 (단위/TDD 테스트 합산 금지)
- [ ] 테스트 함수 주석에 AI 작성 정보와 리뷰 상태(Human in the Loop) 태그가 있는가
- [ ] 의미 없는 테스트가 없고 Stub/Mock 의존이 최소인가
- [ ] 통합 전략과 순서가 기록되어 있는가

## 7. 시스템 테스트 (SWE.6)
- [ ] 모든 테스트 케이스가 존재하는 요구사항 ID를 참조하는가 (역방향 추적)
- [ ] **요구사항 커버리지 100%**: 모든 요구사항이 [제안]이 아닌 케이스로 1개 이상 덮이는가
- [ ] 미결 사항(테스트 불가 요구사항)이 0건인가 (남아 있으면 100% 미달로 판정)
- [ ] 입력이 있는 요구사항에 동치 분할과 경계값 분석이 적용되었는가 (분해능 단위 경계값)
- [ ] 다중 파라미터 조합에 PICT가 적용되었는가 (손으로 만든 조합표 금지, 모델·결과 파일 증적)
- [ ] 엣지/WoW 케이스가 검토되었고 안전 메커니즘 요구사항에 고장 주입 케이스가 있는가
- [ ] 각 케이스에 테스트 케이스 ID, 베이시스 ID, 목적, 입력 값(값·단위), 절차, 예상 출력 값, 기법이 있는가
- [ ] 입력은 구체 값이며 기대값은 요구사항 원문에서 도출되었고 판정 기준이 있는가
- [ ] 정의된 테스트 환경에서 실제로 만들 수 있는 입력인가
- [ ] 중복·무의미 케이스가 없고 무효 클래스는 케이스당 하나인가
- [ ] [제안] 케이스가 커버리지 계산에서 제외되었는가
- [ ] 요구사항 ↔ 케이스 양방향 추적이 프로젝트 기준 위치와 일치하는가
- [ ] 시스템 테스트 실행 결과(합격/불합격)가 기록되고 불합격이 없는가
